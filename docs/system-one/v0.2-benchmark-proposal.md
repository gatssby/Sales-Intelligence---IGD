# System One v0.2 benchmark-gated proposal

Status: prepared, not selected or implemented. Every aggregation or rubric change below requires the human benchmark from `system-one-human-labels-v0.1`. The v0.1 pilot artifacts remain immutable baseline evidence.

## What the current artifacts can diagnose

The benchmark can measure per-key accuracy, confusion, F1, confidence/error relationships, chunk-count relationships, review-state relationships and boolean internal disagreement. It cannot reconstruct every chunk-level class or score because the v0.1 result retained aggregate decisions and selected evidence indexes, not all raw chunk decisions.

Available now:

- boolean evidence-positive and evidence-negative chunk counts;
- aggregate objection ambiguity;
- aggregate buyer-intent ambiguity;
- call chunk count, confidence, probabilities and needs-review state.

Unavailable without a future explicitly versioned output contract:

- exact objection classes emitted by every chunk;
- exact buyer-intent value and range for every chunk;
- transcript duration in the prediction artifact;
- relevance labels for individual chunks.

Do not infer missing chunk-level values.

## Benchmark decision gates

For each decision key, compare candidate policies only on the same frozen human labels and calls. Record rubric, schema, aggregation and dataset versions. Do not choose one global policy for all keys.

A candidate may advance only when it improves the target error mode without materially degrading coverage, minority-class behavior or the frozen review set. Confidence is not correctness; calibration and high-confidence errors must be inspected separately.

## A. Boolean aggregation candidates

The v0.1 evidence-backed OR policy can inflate positives as chunk count grows. Test this by comparing false-positive rate and predicted-positive rate across chunk-count bands.

Candidate policies to evaluate per key:

1. minimum number of supporting chunks;
2. minimum maximum confidence;
3. confidence-weighted support versus contradiction;
4. supporting proportion among relevant chunks;
5. a decision-specific confidence gate with human-review abstention.

The benchmark must determine thresholds. Do not select a threshold from intuition or tune it on the frozen test set.

## B. Objection representation

Keep `objection_type` single-choice in v0.1 benchmarking. For v0.2, evaluate independent multi-label detectors:

- `price_objection_present`
- `timing_objection_present`
- `trust_objection_present`
- `authority_objection_present`
- `fit_objection_present`
- `other_objection_present`

A later deterministic layer may derive `primary_objection`, but it must not discard the multi-label facts. Migration requires a new schema and rubric version and a separately labeled dataset.

## C. Buyer intent

V0.1 selects the maximum observed chunk score, which can bias long calls upward. The current outputs cannot reconstruct exact per-chunk ranges, so this hypothesis must be tested in a future version that retains private chunk decisions.

Candidates:

- `buyer_intent_initial` and `buyer_intent_final` plus `intent_delta`;
- one intent value with explicitly higher temporal weight near the end of the call;
- a relevance-filtered intent classifier followed by a calibrated aggregate.

Choose only after whole-call human labels and, if the schema changes, newly collected temporal labels.

## D. Relevance-first architecture

Proposed experimental path:

```text
transcript
→ physical chunks
→ relevance detector per decision key
→ relevant chunks only
→ typed decision classifier
→ decision-specific aggregation
→ confidence/abstention gate
```

Measure whether this reduces false positives, ambiguity, processed chunks and latency without reducing labeled coverage. Relevance output is not ground truth unless humans label it.

## Future Laya × Jev experiment

Do not invoke Jev until separately authorized. The future experiment must use:

- the same frozen calls;
- the same transcript version;
- the same human label contract;
- the same decision schema and rubric versions;
- separate provider outputs with latency, usage and cost metadata.

Report per decision key:

- human × Laya metrics;
- human × Jev metrics;
- Laya × Jev raw agreement;
- provider disagreement set;
- confidence and calibration;
- latency and throughput;
- Jev usage and cost.

Do not declare a global winner. A future router may map `decision_key → empirically supported engine`, but productive routing requires an ADR, benchmark evidence and safe fallback semantics.

## Active learning design

After the initial frozen benchmark, prioritize human review for:

- Laya and Jev disagreement;
- low confidence;
- needs-review outcomes;
- rare classes;
- recurring benchmark errors;
- examples near a measured decision boundary.

Reserve 10–20% of each labeling batch for randomly sampled high-confidence predictions to detect confidently wrong behavior. Predictions never become truth.

## Fine-tuning design

No training is authorized by this document. A future versioned dataset should record:

- `dataset_version`
- `rubric_version`
- `schema_version`
- labeler identifier
- label timestamp
- source call identifier
- split assignment

Split by call, never by chunk. No chunks from one call may cross train, validation or test. Evaluate leakage controls for seller, time period and product. Keep a frozen test set that threshold selection, rubric editing and fine-tuning cannot use for optimization.
